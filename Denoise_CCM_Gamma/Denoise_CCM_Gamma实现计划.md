# Denoise_CCM_Gamma 实现计划与设计讲解（M5.2）

> 面向"为什么这么设计"，而不是"怎么用"。用法/接口/复现命令见 [README.md](README.md)。
> 本模块的产出不只是"把三个模块串起来"，而是**一个能回答 ISP 链路顺序问题的可复现实验**。

---

## 一、任务边界

- **做**：把 M4 的 `denoise_stage` → `ccm_stage` → `gamma_stage` 串成一级工程件（30bit 线性 RGB 进、RGB888 出），
  并支持"降噪 / CCM 互换"做对照实验。
- **不做**：不接 BLC/DPC/Demosaic/锐化（那是整链 M5.2+ 的事），不做 CDC/AXIS 适配（M5.1 的 `AxisOut` 已覆盖）。
- 交付：`rgb_chain_top.v` / `tb_rgb_chain.v` / `make_chain_data.py` / `verify_chain.py` + 两套 golden + 对比图。

## 二、为什么"顺序问题"必须用实验回答，而不是讲道理

**理论层面先给出必然结论：两者不可交换。**

- 双边降噪是**非线性**算子：值域权重 `wr = LUT[d]`，而 `d = |ΔR|+|ΔG|+|ΔB|` 依赖像素值本身
  ⇒ `F(a·x) ≠ a·F(x)`，不满足线性性
- CCM 是**线性**矩阵乘（Q5.12 定点 + round + 饱和）
- ⇒ `CCM ∘ 降噪 ≠ 降噪 ∘ CCM`（`linear∘nonlinear` 交换律不成立）

所以"能不能换"是**已经确定的答案**（不能）。真正有信息量的问题是**"谁在前更好、好多少、为什么"**——
这只能量化回答。

### 更要命的陷阱：定点饱和让"理论等价的顺序"也可能不等价

即使把 CCM 当成纯线性算子，它在 RTL 里有 `sat[0,1023]`：

- **降噪在前**：先压掉噪声 → CCM 的输入更"温和" → 撞饱和的样本少
- **CCM 在前**：CCM 先把噪声放大（对角线 >1、且负系数会把三通道噪声混进来）→ 更多样本被推到 0/1023
  → **一旦被裁掉，信息就永久丢失**，后级降噪再厉害也补不回来

这就是为什么顺序之争不能只看算法教科书，**必须带定点/饱和一起算**。

## 三、实验设计（公平性是第一原则）

| 设计要点 | 做法 | 为什么必须这样 |
|---|---|---|
| **单一变量** | 只用一个参数 `SWAP_DC` 切换顺序，例化/参数/激励/判据全部相同 | 否则差异可能来自别处，结论不可信 |
| **总延迟相等** | 降噪 7 + CCM 2 + Gamma 1 = 10；互换后 2 + 7 + 1 = 10 | 延迟相等 ⇒ 两种顺序的流出流可**逐拍对齐**，不需要额外补偿，也使"位级差异"纯粹来自算法顺序 |
| **参考基准** | 与**无噪声理想图** `ideal = Gamma(CCM(clean))` 比 PSNR/SSIM | 只有一个客观靶子才能判"谁更好"，否则只能比"谁和谁不一样" |
| **对照组** | 额外造 `base = Gamma(CCM(noisy))`（**不降噪**） | 用来量化"降噪一共带来多少改善"，把顺序差异放到正确的量级里看 |
| **数据一致** | 直接复用 `BilateralFilter/denoise_in.hex`（注噪输入）与 `clean_rgb.hex`（干净基准） | 保证链的输入与单模块 TB **逐字节一致**，结果能与 M4 已公布的指标对齐讨论 |
| **双判据** | TB 位级比对（第一判据）+ `verify_chain.py` 独立重算（第二判据） | 防止"TB 期望照抄 DUT 表达式 → 两边同错、逐位比对照样通过" |

## 四、接口与定点细节

1. **30bit 打包 = `{R,G,B}`（R 在高位）**，24bit = `R G B` 各 8bit。
   证据：`gamma_stage.v` 的 `in_data[3*DW-1 -: DW]`、`make_ccm_data.py` 的 `(p >> 20) & MAXV`。
2. **位宽缩减只在 Gamma 出口发生**（30bit → 24bit）——这是 M4 定下的"全链唯一换位宽"架构点，
   所以三段链的输出天然就是 VDMA 要的 RGB888，不需要额外收尾。
3. **各级 bypass 语义不统一**：`bp_denoise` 是**帧级**（含行缓存，只能排空点切换），
   `bp_ccm`/`bp_gamma` 可**任意拍**。链顶层把三个 `bypass` 都引出来，但语义必须按各模块文档使用。
4. **链首 `in_ready` 随顺序变**（谁在链首谁给出），所以顶层先用 `first_rdy` 局部 wire 再驱动端口
   —— 直接把端口接到 generate 分支里多处驱动会踩双驱动。
5. **节点命名用"级名"而不是"第几级"**（`dn_*` 恒为降噪输出、`cc_*` 恒为 CCM 输出），
   再用 `assign g_* = (最后那一级)` 送 Gamma。这样两个 generate 分支可读性一致、不易错。

## 五、结果与解读

### 5.1 位级：不可交换（98.2% 像素不同，max 67，MAD 2.88）

非零差异本身就是"顺序有意义"的证据。**如果两边位级相同，就说明其中一个算子退化了**
（比如 CCM 接近单位阵、或降噪被 bypass），"顺序之争"也就无从谈起。

### 5.2 质量：顺序0 更好 1.51 dB

| 变体 | PSNR | SSIM | 色差 (R−G) 梯度 RMS |
|---|---|---|---|
| 无噪声理想 | ∞ | 1.0000 | 17.263 |
| 不降噪基线 | 23.11 dB | 0.7918 | 48.441 |
| **顺序0 降噪→CCM** | **28.67 dB** | **0.9323** | **17.812** |
| 顺序1 CCM→降噪 | 27.16 dB | 0.9147 | 26.316 |

两个读法：
- **降噪的收益**：28.67 − 23.11 = **+5.56 dB**（相对不降噪基线）
- **顺序的代价**：28.67 − 27.16 = **1.51 dB**（把降噪放在 CCM 之后要付的代价）
- **色噪声残留**：顺序0 几乎回到理想水平（17.81 vs 17.26），顺序1 仍比理想高 **52%**

### 5.3 原因（两条独立机理）

**机理 A · CCM 放大并裁掉噪声（数值域）**

对角线系数 >1（本工程设计矩阵 `[1.72 −0.62 −0.10; −0.24 1.44 −0.20; …]`）⇒ 矩阵乘对噪声是**放大**的；
负系数还把三通道噪声**混合**起来。实测 CCM 输出撞到 0/1023 的样本数：
**降噪后喂 CCM = 75** vs **噪声直喂 CCM = 381（5.1 倍）**。裁掉就是永久损失。

**机理 B · 色噪声让双边滤波"认错边缘"（算法域）**

双边滤波的值域权重按 `d = |ΔR|+|ΔG|+|ΔB|` 查 LUT——它假设"相似像素的 d 小"。
噪声直喂 CCM 后，噪声被染成**通道相关**的色噪声，d 的分布被抬高、像素间"看起来不像"，
于是 `wr` 变小、滤波退化成"近高斯"，噪声被当成"边缘"保护下来。
实测色差梯度 RMS 从理想的 17.26 涨到 26.32（顺序1）就是这条机理的体现。

> 有意思是机理 A 和 B 指向同一个结论，但**改一个都不够**：把 CCM 的饱和去掉，机理 B 还在。
> 所以"降噪在 CCM 前"不是"躲开饱和"的技巧，而是**噪声形态学**的选择。

### 5.4 结论（可对外讲的版本）

> 降噪与 CCM **不可交换**（非线性 ∘ 线性），且**降噪应在 CCM 之前**：
> 一是 CCM 会把噪声放大并推向饱和边界（饱和样本 5.1 倍），裁掉即丢信息；
> 二是 CCM 会把通道独立噪声变成通道相关的**色噪声**，破坏双边滤波"以亮度差判相似"的前提，
> 使降噪退化。实测两者差 **1.51 dB PSNR**，色噪声残留差 **1.48 倍**。

## 六、踩坑

**坑 1 · `$readmemh` 按"运行目录"相对寻址 → 链顶层编译/运行都得多带路径**

- **现象**：链目录里编译报 `Include file denoise_stage.v not found`；即使编译过，`vvp` 也读不到 `.coe`
- **根因**：两个不同的相对寻址机制：`include` 走 `-I` 编译期搜索；`$readmemh` 走**运行时的 CWD**
- **修法**：编译加 `-I ..\BilateralFilter -I ..\CCM -I ..\Gamma`（外加既有的 `line_buffer`/`fifo`）；
  并把 4 个 `.coe` **复制**到链目录（真源仍在各模块，重新生成后需再复制）
- **教训**：跨模块串联时，"文件路径"有两套解析规则，别只想到 `-I`

**坑 2 · 链首 `in_ready` 在 generate 里多处驱动**

- **现象**：直接用 `output in_ready` 在 `if/else` 两个分支里接不同模块，工具报多处驱动
- **修法**：先用 `wire first_rdy` 承接，再在模块级 `assign in_ready = first_rdy;`

**坑 3 · 数据一致性靠"复用"而不是"重造"**

- **现象**：如果在本目录重新注一遍噪声，RNG 消费顺序稍有不同就会得到**另一张噪声图**，
  于是与 M4 已公布的数字失去可比性
- **修法**：img 模式**直接加载** `BilateralFilter/denoise_in.hex` 与 `clean_rgb.hex`，
  并 assert 尺寸；换来的是"链的输入与单模块 TB 逐字节一致"
