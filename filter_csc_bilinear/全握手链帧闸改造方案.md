# 全握手链 + 帧闸改造方案（filter_csc_bilinear 升级）

> 针对 README「可改进/受限点」第 1、2、3 条的统一改造方案与可行性评估
> 结论先行：**三个问题同源（无背压流水的系统级缺陷），一次"全握手链 + 帧闸"改造可同时解决**，详见第三节论证。

---

## 一、三个问题与同源性

| # | 问题 | 本质 |
|---|---|---|
| 1 | 整帧 FIFO 资源大（2^14×24bit ≈ 22 块 BRAM18K） | 用"缓冲"掩盖速率差 |
| 2 | 无背压→全握手改造（AXI-Stream 标准答案） | 用"反压"管理速率差 |
| 3 | 多帧流不可直接复用（需帧闸） | 缺帧级协议（start 与数据、帧与帧的边界管理） |

**同源性**：高斯/中值/CSC 是"每拍进 1 出 1"的无背压流水，缩放又必须按自己的节奏消费——系统里**生产者不可暂停**，就只能①让消费者等（帧缓冲）或②让生产者会暂停（握手）。问题 3 的帧闸则是握手协议的天然配套（帧与帧之间需要明确的"何时可以再来一帧"信号）。**一次架构升级（握手链 + 帧闸）把 1、2、3 一起解决**，而不是三个孤立的补丁。

---

## 二、为什么"小 FIFO"方案救不了问题 1（速率不等式）

先排除一个看起来省事的方案：把大 FIFO 缩成几行。设输入帧 N 像素，放大 2 倍时缩放模块平均每消费 1 个输入像素需要 4 个输出拍（输出 4N 像素 / 拍）：

```
生产者速率（无背压）= 1 像素/拍
消费者平均速率 = 1 像素/4 拍 < 生产者速率
```

有限缓冲 B << N 时，生产者在 N 拍内必填满 B 而消费者只消费了 N/4 → 溢出。**只要消费者平均速率低于生产者，且生产者不可暂停，缓冲就必须 ≥ 一帧（N）**——这就是当前 22 块 BRAM 的数学根源。所以问题 1 的"缩成几行"在数学上不成立，**唯一出路就是问题 2 的全握手（生产者可暂停）**。

## 三、目标架构（三问题一并解决）

```
输入帧协议：start(帧启动) + din/din_valid/din_ready（握手像素流）
  │ 帧闸 FSM（见下）
  ▼
gaussian_axs（握手版） ─► median_axs（握手版） ─► csc_axs（握手版）
  │ 每级：out_valid/out_ready 双向握手；反压沿 valid 链逐级回传至 din_ready
  ▼
[可选 小弹性 FIFO，深度 4~16] ─► bilinear_lb_top（v4 原封不动——它本来就是握手模块！）
  ▼
o_dout/o_valid/o_ready（输出侧也带反压）+ o_done（帧结束）
```

**关键洞察：缩放模块（bilinear_lb_top）已经是完整的握手模块（din_valid/din_ready 双向）**——真正的改造对象只有三个无背压环节：行缓存 + 高斯核 + 中值核 + CSC。全握手后：

- **问题 1 → 解决**：生产者可暂停后，FIFO 从"整帧容量"降为"纯时序弹性缓冲"（可选保留 4~16 深度吸收握手往返抖动，也可完全去掉——见决策点 D1）
- **问题 2 → 解决**：全链 valid/ready 握手，AXI-Stream 标准
- **问题 3 → 解决**：帧闸 FSM 管理帧边界（见下），连续帧可复用

### 帧闸 FSM（问题 3）

```
状态: IDLE → RX → FLUSH → IDLE
IDLE : 允许外部拉 start（frame_start 由本 FSM 输出的 frame_start_ok 门控）
RX   : din_ready=1 接收整帧；输入侧帧尾（外部 vsync 风格信号或行/列计数到帧末）→ FLUSH
FLUSH: 等全链在途数据排空（o_done 脉冲 && 输出侧无 pending valid）→ 回 IDLE
```

- 连续帧：上游在 `frame_start_ok`（= IDLE）时才能拉下一帧 start——即"上一帧完全排空后下一帧才允许进来"，等价于 README 建议的"FIFO empty 才允许下一帧 start"，且更严格（全链无在途）
- 数据与流水：RX 期间握手链自然管理（缩放反压 → din_ready=0 → 帧闸暂停接收，不会丢）

### 模块改造清单（核与行缓存的 stall 原理）

**可行性前提（已验证）**：行缓存 `line_buffer_3x3` 的窗口寄存器在 `din_valid=0` 时保持（`else if (din_valid)` 结构）——**din 停 → 窗口停 → 核输入保持**，天然支持停流。核的 `valid_chain` 是简单移位链。

| 模块 | 改造 | 改动量 |
|---|---|---|
| `line_buffer_axs` | 端口加 `in_ready`：无窗口输出时恒 1；有窗口输出时 = 下游核的 ready（窗口保持语义保证不丢） | ~5 行 |
| `gaussian_axs_8b` / `median_axs_8b` | 端口加 `out_ready`；内部"整流水冻结"：`run = out_ready | ~out_valid`，所有级寄存器与 valid 链使能 = run | 每核 ~8 行 |
| `csc_axs`（或 3stage 加参数） | 4 级流水加逐级 stall 使能（out_ready 沿流水回传） | ~15 行 |
| `top_chain2.v`（或 top_chain 参数化） | 例化握手版全套 + 帧闸 FSM + 可选小 FIFO | ~60 行 |
| `bilinear_lb_top` | **零改动**（已是握手模块） | 0 |
| `tb_chain2.v` | 随机 `out_ready` 反压压力 + 连续两帧帧闸测试 | ~40 行 |

**stall 正确性要点**（核内）：

```verilog
// 输出反压时整条流水冻结（全停或全进，无半推进）
wire run = out_ready | ~out_valid;
always @(posedge clk) begin
    if (!rst_n) ...
    else if (run) begin
        // 各级寄存器推进 + valid 链移位
    end
end
// din_ready = run 传播到行缓存侧（行缓存窗口保持由 din 停保证）
```

## 四、三问题同时解决评估

| 评估项 | 结论 |
|---|---|
| 数学可行性 | ✅ 生产者可暂停打破了"缓冲 ≥ 一帧"的不等式，大 FIFO 可移除 |
| 技术可行性 | ✅ 行缓存窗口可保持（寄存器语义）、核 valid 链可加 stall、CSC 是标准 4 级流水可 stall 化、缩放本来就是握手模块——全部有现成模式 |
| 死锁风险 | ✅ 单时钟域 + ready 组合单向回传（valid 由寄存器产生、ready 组合传递），不存在组合环；缩放侧沿用 v4 已证明的 wr/rd 双反压不死锁机制 |
| 帧闸与握手配套性 | ✅ 帧闸只是"start 与排空的仲裁"，握手链提供"排空可观察"（o_done + 无 pending valid） |
| 一次改造的成本 | 新建握手版模块（~130 行）+ TB/验证适配（~40 行），**既有模块与五处副本零改动**（不破坏历史验证） |
| 结论 | **三个问题可以一次改造同时解决**，且是唯一正确的解决路径（小 FIFO 方案在问题 1 上行不通，见第二节） |

## 五、实施步骤与验证计划

1. `line_buffer_axs.v`（in_ready 透传）→ 单级自检：随机 out_ready 下像素不丢（对比无反压基线）
2. `gaussian_axs_8b.v` / `median_axs_8b.v`（核 stall + 行缓存）→ 单级自检同上 + 位级全等保持（实现精度仍应 inf）
3. `csc_axs.v` → 单级自检
4. `top_chain2.v`（握手链 + 帧闸 + 可选小 FIFO）→ 级联验证（两种 ORDER 恢复度应于现工程数值一致，证明"结果不因架构改变而变"）
5. **连续两帧测试**：帧 2 在帧 1 done 后立即 start，两帧像素数 = 2 帧独立之和、帧间无串扰（帧闸验收）
6. 资源对比：vivado 综合对比"改造前（22 块 BRAM）vs 改造后（0 或 4~16 深度）"，量化问题 1 的收益
7. README 更新：架构说明、帧协议、资源对比数据

**回归基线**：现工程（seed=20260819）的恢复度表（13.59/19.74/20.66/18.23/18.69 与 swap 21.45）是改造后必须复现的数值——架构变化不应改变算法结果（指令集不变）。

## 六、风险与回退

| 风险 | 缓解 |
|---|---|
| stall 与 valid 链错位（本项目老坑） | 位级全等回归（实现精度必须仍 inf）+ 随机反压压力下像素数/全等双重断言 |
| 帧闸 FSM 边界（done 脉冲过早——见 README B2：done 超前 9 拍） | 帧闸 FLUSH 判定 = o_done AND 输出侧无 pending valid，不依赖单脉冲 |
| 组合 ready 链过长（级联路径时序） | 可选保留 4~16 深度小 FIFO 打断长链（决策点 D1） |
| 改造规模失控 | 分步合入：每级独立自检 PASS 才进下一步；failure 时回退到当前整帧 FIFO 版（git/备份） |

## 七、决策点（实施前确认）

- **D1 FIFO 去留**：A=纯握手链（0 BRAM，链路着手时序）｜B=保留 4~16 深度小 FIFO（推荐：断开长 ready 组合链，资源从 22 块降到 <1 块）——推荐 B
- **D2 模块形态**：新建 `*_axs` 握手版（不动权威版，推荐）vs 给现有模块加参数开关（侵入五处副本）
- **D3 帧闸位置**：链路顶层内建（top_chain2，推荐）vs 外部 TB 控制（不算系统级解决）
- **D4 验证强度**：位级全等（实现精度 inf）+ 连续两帧 + 随机反压三重门槛（推荐）

## 八、改造前后资源收益预估

| 项目 | 现在 | 改造后（D1=B） |
|---|---|---|
| 速率匹配 FIFO | 16384×24bit ≈ **22 块 BRAM18K** | 8~16×24bit ≈ **0~1 块** |
| 握手协议 | 仅缩放内建 | 全链 AXI-Stream |
| 帧支持 | 单帧 | 连续帧（帧闸） |
| 模块可复用性 | 无背压特例 | 标准握手，可对接任何 AXI-Stream 上游/下游 |
