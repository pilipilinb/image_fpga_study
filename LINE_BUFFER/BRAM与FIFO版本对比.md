# 3x3 行缓存：手写 BRAM 版 vs FIFO IP 版对比

> 对比对象：
> - **BRAM 版**：`line_buffer_3x3.v`（推断式 BRAM + read-first + 手动打拍对齐）
> - **FIFO 版**：`fifo_line_buffer3x3.v`（3 个 FIFO IP 级联，深度 = 行宽）

---

## 1. 核心原理对比

| 维度 | 手写 BRAM 版 | FIFO IP 版 |
|---|---|---|
| 行延迟机制 | read-first 同址读写：读旧值（上一行）同拍写新值（当前行） | FIFO 深度 = 行宽(480)：写满即读、读写 lockstep，水位恒定一行 |
| 地址管理 | 自己管 `col_cnt`，且要逐级打拍（`col_d1`） | 无地址概念，读出顺序 = 写入顺序 |
| 列对齐方式 | **显式打拍**：din/col/valid 逐级对齐 BRAM 读潜伏 | **结构保证**：深度锁死一行差距，天然同列 |
| 拍级延迟 | 显式处理（din_d1/din_d2 打拍链） | **藏在 FIFO 配置里**：必须 FWFT 模式；标准模式每级斜 1 像素，需手动补拍 |
| 气泡（valid 不连续） | 每级用对应级 valid 门控 | rd_en = 写满 && valid_in，读写同冻结，天然处理 |

## 2. 资源与性能

| 维度 | 手写 BRAM 版 | FIFO IP 版 |
|---|---|---|
| 存储 | 2 块 BRAM（N×N 窗口只需 N-1 条行缓存） | 3 个 FIFO（本质也是 BRAM，多一条冗余行 + 空满/计数逻辑） |
| 附加逻辑 | 少量打拍 FF + 计数器 | 每个 FIFO 带空满标志、水位计数、FWFT 输出缓冲 |
| 时钟频率 | 打拍充分，易收敛 | FIFO IP 内部已优化，易收敛 |
| 结论 | **资源最省** | 略费（多一行存储 + 控制逻辑 ×3） |

## 3. 开发与验证

| 维度 | 手写 BRAM 版 | FIFO IP 版 |
|---|---|---|
| 开发量 | 大：要自己推"每拍谁在哪"的对齐表 | 小：调 IP + generate 级联 |
| 易错点 | 打拍漏一级 → 错一列（**坑在代码里，review 可见**） | FIFO 读模式选错（FWFT vs Standard）→ 每级斜 1 像素（**坑在 IP 配置界面，代码 review 看不见**） |
| 可移植性 | 纯 RTL，跨平台 | 绑定厂商 FIFO IP（Xilinx/Altera 接口不同） |
| 复位 | BRAM 阵列不可复位，输出寄存器同步复位 | FIFO 复位有 busy 周期（`wr_rst_busy`/`rd_rst_busy`），复位后需等待 |
| 验证 | 必须仿真 | **同样必须仿真**（IP 配置错误只有仿真能抓） |

## 4. 边缘 Padding 能力 ⚠️

**先纠正一个误区：FIFO 版不是"没法 padding"，而是"没法用地址法 padding"。**

Padding 的三种实现路径，两版的支持情况：

| Padding 方法 | 原理 | BRAM 版 | FIFO 版 |
|---|---|---|---|
| ① 窗口级 mux（推荐） | 在 3x3 窗口输出后，根据 row/col 坐标用 mux 复制边缘行/列（replicate）或镜像（mirror） | ✅ | ✅ 两版此处逻辑完全相同（窗口成型在缓存下游） |
| ② 输入流预 padding | 顶层先把图像流扩成 (H+2)×(W+2)（边缘像素复制后再灌入），行缓存只输出"内部"窗口 | ✅ | ✅ 与缓存实现无关 |
| ③ 地址钳位法 | 读 RAM 时把越界地址钳到边界（如 `col-1 < 0` 时读地址 0） | ✅ 有地址，可任意钳位/重读 | ❌ **无地址、不能重读**——这是 FIFO 唯一做不到的 |

**FIFO 版真正的痛点是"尾行 flush"**：最后一行输入结束后，`valid_in` 永久拉低，而 `rd_en = (cnt==行宽) && valid_in` 与输入绑死 → FIFO 里还压着最后两行数据读不出来，底边 padding 窗口无法生成。要支持底边，必须**额外加 flush 状态机**（输入结束后强制持续 `rd_en`，并补造 valid），破坏了原代码"读写严格同步"的简洁性。BRAM 版同样需要 drain 逻辑，但因为地址自主可控，flush 实现更直接。

**结论**：
- 只要 padding 用①或②（工程上 99% 的场景），两版能力等价；
- FIFO 版丧失的是**随机访问能力**（地址法、重读、跳读），以及**尾行 flush 需要额外破坏读写同步的逻辑**；
- BRAM 版的窗口级 replicate padding 已实现：`line_buffer_3x3_pad.v`（输出 H×W 个窗口，上/左边用输出 mux 复制，右/下边靠 h-blank/v-blank 空拍插 flush 拍，仿真 96 窗口 0 错误）。原版 `line_buffer_3x3.v` 保留为无 padding 基线（输出 (H-2)×(W-2) 内部窗口）。

## 5. 选型建议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 资源紧张 / 面试手写 | BRAM 版 | 最省资源；能讲清打拍对齐是硬实力 |
| 快速出原型 / 团队协作 | FIFO 版 | IP 成熟，开发快，代码量小 |
| 需要地址级操作（钳位 padding、ROI、跳行） | BRAM 版 | FIFO 无随机访问 |
| 跨厂商移植 | BRAM 版 | 纯 RTL 不绑 IP |
| 深度不定/跨时钟域行缓存 | FIFO 版 | 异步 FIFO 现成，手写 CDC 成本高 |

## 6. 面试一句话总结

> BRAM 版靠 read-first + 显式打拍换最省资源，坑在代码里；FIFO 版靠"深度=行宽、写满即读"把列对齐结构化，坑在 IP 配置里（必须 FWFT）。Padding 层面两者窗口级 mux 能力等价，FIFO 仅丧失地址钳位和便捷 flush。选型看资源、移植性和是否需要随机访问。
