## 与 v3 对比

| 维度 | v3 整图 ROM | v4 行缓存 |
|---|---|---|
| 存储 | 整帧 × 4 份（随图像尺寸线性膨胀） | **3 行 × 行宽**（恒定，随行宽） |
| 输入方式 | 整帧就绪（$readmemh）再随机读 | **流式输入**（din/din_valid，边进边出） |
| 读侧 | 任意随机读，零等待 | 行未就绪要等（rd_ready 反压） |
| 写侧 | 无（只读） | 槽位冲突要等（wr_ready 反压） |
| 适用 | 小图学习、整帧可用 | 大图、实时视频流（1920×1080 可行） |

**1920×1080 存储对比**：v3 ≈ 5500 块 BRAM（爆）｜ v4 ≈ 3 块 BRAM（恒定）

## 架构与核心机制

```
din[23:0]/din_valid（流式输入） ──► line_cache2（3 行环形）
                                      │ 写侧：光栅顺序，槽位冲突检查反压
  coord_gen（pixel_en = rd_ready）──►│ 读侧：按源坐标 (sy,sx) 组合读 4 邻居
                                      ▼
                              钳位/权重清零 ──► 3×bilinear_interp_8b ──► o_rgb + o_valid
```

### 反压两条判定式（核心）

```verilog
// 写侧：槽位 w%3 的旧行(w-3)已被读侧滑过才允许覆盖（读侧停滞后仍能写完剩余行）
assign wr_ready = ((w < 3) || (sy00 > w - 3)) && (w < IN_HEIGHT);
// 读侧：窗口顶行 sy+1 已写完
assign rd_ready = (sy01 < w);
```

- 放大（写快读慢）：写侧追上读窗口后暂停，等读侧滑动释放槽位
- 缩小（写慢读快）：读侧等行写完，输出暂停
- 帧末排空：读侧完成后写侧仍能写完剩余行（旧行已被滑过）——不会死锁

## 调试记录（重要）

1. **帧末排空死锁（已修）**：初版 `wr_ready = (w <= sy01)` 在缩小场景读侧先完成、`sy` 停住时卡死写侧（输入未喂完）。改为**槽位冲突检查**（`w-3` 旧行是否被滑过）后，读侧停顿写侧仍能写完剩余行。
2. **输出 COE 竞态（已修）**：TB 写 COE 用记分板 `out_cnt` 判断，与计分板跨 always 竞态导致最后一个像素漏写。改为独立写计数 `w_cnt`。（v3 TB 存在同款隐患，建议同步修复。）

## 技术易错点（面试问答）

> 面试官问"实现时遇到过哪些问题"时，从下面挑 2~3 个讲：现象 → 根因 → 解法，最后背一句收尾。

### 1. 行缓存反压死锁（本工程最核心的一个坑）

- **现象**：缩小场景下仿真超时（卡在输入侧），COE 文件恰好少最后 1 行。注意：**输出像素其实一个没少**，详细的澄清见下方案例推演之后。
- **根因**：写侧反压用的是"游标相对位置"规则 `wr_ready = (w <= sy01)`，它隐含"读侧会继续推进"。缩小场景读侧（输出）**先完成任务**，sy 停住不再变 → 写侧被永久卡住，最后一行输入喂不进去。
- **解法**：反压判定改成**槽位实际占用**：写行 w 前检查它要覆盖的格子里旧行（w-3）是否已被读侧用完（`sy00 > w-3`）。读侧停住也不怕，因为它早把旧行消费完了。
- **💬 面试一句话**："环形缓冲的反压不能靠游标相对位置，必须检查槽位里旧行是否被消费完——否则消费者先停（帧末/缩小）时生产者会死锁。"

**完整案例推演：缩小 1/2 时的死锁现场（112×103 → 56×51）**

先交代背景——三个角色（都是 v4 工程里的）：

- **输入侧（写侧）**：把 103 行像素一行一行送进 3 格子的缓存，光栅顺序。
- **输出侧（读侧）**：按源坐标 (sy,sx) 从缓存取 2 行 × 2 列做插值，输出 51 行。
- **出 bug 的规则**：`wr_ready = (w <= sy01)`——写侧最多写到"读窗口顶行 sy01"，再多就等。

按时间线走一遍，看死锁怎么一步步发生：

1. **输入送多少？——103 行全送**。103 是源图固定行数（IN_HEIGHT=103），输入流把整幅图逐行灌进来，不是"只送输出用得到的行"。
2. **读侧在哪一行停？——输出最后一行 dy=50 处**。输出行数 = 103÷2 = 51（取整），最后一行是 dy=50。它要采样的源位置：STEP_Y = (103×256+25)/51 = 517，dy=50 → sy_a = 50×517 = 25850 → sy = 25850÷256 = 100（小数 0.98 被丢掉）。所以读窗口停在 {100, 101}（sy00=100，sy01=101）。
3. **写侧当时写到哪？——w=102，还差最后一行**。旧规则允许 w ≤ 101，写侧写完 0..101 后 w 变成 102，被 `102 ≤ 101` 挡住，停下来等 sy01 变大。
4. **为什么永远等不到？——死锁**。读侧干完活了，sy 冻结在 100、sy01 冻结在 101，永远不会变大 → 写侧等不到条件重新成立。可输入流还有第 102 行（112 个像素）排队没送完——这一行输出采样永远用不到（采样只走到 100.98），是"残渣行"，但输入流必须把它全部收走（握手协议）。写侧不收 → 输入侧 while(!in_ready) 死等 → 仿真超时。

**死锁现场一句话**：读侧收工、写侧被规则卡在差一行、输入侧还有一行没人接——三方互相等。

**为什么放大场景不会死锁**：放大时读侧（输出）慢、最后才收工，写侧始终在等读侧推进，不存在"读侧先停"，所以这个 bug 只在缩小（输出先完成）场景触发。

**解法衔接**：把规则改成"槽位占用检查"（`sy00 > w-3`，即我要覆盖的旧行读侧用完没）后，写侧不再跟 sy01 比大小——读侧收不收工都不影响写侧把最后一行收完，死锁解除。

**重要澄清：输出像素其实一个没少**

死锁卡在"输入侧"，不是"输出侧"。那次超时的诊断打印（TB 超时兜底里加的）：

```
w=102  sy=100  sy01=101  rd_ready=1  wr_ready=0  in_ready=0  o_valid=0  out_cnt=2856
```

- `out_cnt=2856`：输出像素**全部算完**（2856 = 51×56，一个不少）；`o_valid=0`：输出已收工。
- 卡住的是输入：还有第 102 行（112 个像素）在缓存门口没人接，TB 的 `while(!in_ready)` 死等，主流程走不到"正常结束"，触发超时。
- 仿真正常结束需要两个条件同时成立：**输入全部喂完 + 输出全部取完**。这里输出完成了，输入还欠一行，流程就收不了尾。
- "COE 少 1 行"是超时打断（文件没 flush 完）+ TB 写文件跨 always 竞态（见第 5 条，另一个独立 bug）叠加的结果，**不是输出丢像素**。两个 bug 都修掉后，输出 2856 像素 + COE 2856 行全部正确。

### 2. BRAM 同步读的 1 拍潜伏导致数据错位

- **现象**：reg 数组改 BRAM 后，输出全错（加权值和像素对不上）。
- **根因**：reg 数组是**组合读**（地址到、数据立刻出，0 拍延迟）；BRAM 是**同步读**（地址 T 拍给、数据 T+1 拍出）。4 个邻居晚 1 拍，而权重/valid 还是当年那拍 → 错位。
- **解法**：把 u/v/valid/钳位标志**补 1 拍对齐寄存**再喂插值核（v3 用 ROM 时本来就有这 1 拍，直接抄回来）。
- **💬 面试一句话**："换存储介质必然改变读时序：组合读 0 拍、BRAM 同步读 1 拍，顶层所有要对齐的信号都得跟着补拍。"

### 3. BRAM 一块只有 1 写 1 读，读 4 邻居凑 2 个读口

- **现象/根因**：双线性要读 2 行 × 2 列，即一次要读 sy 行和 sy+1 行的 sx、sx+1 两列——4 个读。一块 BRAM 只有 1 读口，不够。
- **解法**：每行放 2 块内容镜像的 BRAM（一块专读 sx 列、一块专读 sx+1 列），3 行共 6 块，1 拍取齐；或者每行 1 块分 2 拍读（省存储、吞吐减半）——面积换速度 vs 速度换面积。
- **💬 面试一句话**："BRAM 的读写口是体系的硬限制，多读口要么镜像多块、要么分时复用，没有第三种。"

### 4. BRAM 阵列不可复位（推断铁律）

- **现象/根因**：BRAM 原语没有内容复位引脚。给存储数组加复位条件，综合器就不认它是 BRAM，退化成一堆 LUT/FF。
- **解法**：存储数组**不加任何复位**；读输出寄存器用**同步复位**（`if(!rst_n)` 写在 `posedge clk` 内、不进敏感表）；上电脏数据靠 valid 门控屏蔽。
- **💬 面试一句话**："BRAM 阵列物理上不可复位，只能复位读输出寄存器，脏数据靠 valid 门控挡掉——加了复位反而推断失败。"

### 5. TB 写输出文件跨 always 竞态（最后一行漏写）

- **现象**：TB 自检全对，但 output.coe 恰好少 1 行，校验脚本报尺寸不匹配。
- **根因**：写文件的 always 直接读记分板的 `out_cnt` 做判断，两个 always 在时钟沿后的执行顺序不定——写文件块先执行时，最后一个像素被当成"超帧"跳过。
- **解法**：写文件块用**自己独立的写计数**（`w_cnt`），不共享记分板变量。
- **💬 面试一句话**："TB 里跨 always 共享计数是竞态温床，写文件要独立计数，否则依赖调度顺序会偶发丢数据。"

### 6. 通用教训：反压/对齐这类"协调逻辑"最容易出 bug

- 本工程一半的调试时间花在"写读协调"上（死锁、错位、竞态），而不是算法本身——算法（双线性）一次就对了。
- **💬 面试一句话**："图像算法本身不难，难的是流水线对齐、存储读时序、写读反压这些工程细节；我的验证方法是不但要功能对，还要专门造压力用例（插气泡、极端缩放比）把它们逼出来。"

```powershell
# 1. 输入数据（从 v3 复制或重新生成）

```

## BRAM 版说明（已实现）

本版 line_cache2 已用**推断式 BRAM**（`ram_style="block"`，不需要任何 IP），行宽大不会爆 LUT。三处实现细节：

| 点 | 实现 |
|---|---|
| ① 存储 | 每行 2 块 BRAM（内容相同镜像），3 行共 6 块 |
| ② 为什么每行 2 块 | 一块 BRAM 只有 1 写 1 读；读侧要读 sx 和 sx+1 两列 → 一块读 sx 列（line_a）、一块读 sx+1 列（line_b） |
| ③ 同步读 1 拍潜伏 | BRAM 是同步读（地址 T 拍给、数据 T+1 拍出），比坐标/权重晚 1 拍 → 顶层已补 1 拍对齐寄存（u/v/valid/钳位标志打一拍再喂核） |

**完全不变**：行就绪（rd_ready）、槽位冲突（wr_ready）、整个反压协调逻辑——只关心"行写没写完、读侧滑没滑过"，跟存储是 LUT 还是 BRAM 无关。
